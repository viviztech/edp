## Database and object recovery consistency

A PostgreSQL dump restoring successfully is insufficient for a platform with immutable records referencing exact private object versions. Design recovery around a recorded database recovery point and a compatible set of available object versions.

1. Define the recovery boundary. Record backup identity/time, schema revision, object inventory recovery point, application/configuration versions and required secret/key references, without embedding secret values. Agree backup frequency/retention and RPO/RTO with operations/privacy owners before configuring real schedules.
2. Protect the sources. Database backup access, encryption keys and object versions need restricted independent recovery paths. Backup/version lifecycle must respect holds and frozen-evidence retention; bucket rules cannot silently remove evidence still referenced by the application. A backup key and the sole backup must not share one uncontrolled failure boundary.
3. Restore only to a fresh isolated database/bucket/namespace with outbound auth/domain messaging, callbacks, Beat and disposal disabled. Preserve any deletion/withdrawal ledger needed to reapply approved deletions after restore; the ledger design is a deliverable, not an existing capability claim.
4. Validate the schema revision, constraints, representative counts/FKs and core application → selection → enrollment → learning/support chains. Check audit continuity, immutable snapshots and domain-owned file references, including legal holds, frozen evidence, retention deadlines and unresolved/quarantined/disposed states.
5. For every referenced file in the synthetic drill, verify that the expected exact object version is available with the recorded checksum/length/encryption and that current authorized domain gateways return the expected bytes. A byte-identical copy with a different provider version ID is not sufficient when the application pins the old version. The recovery design must preserve exact referenced-version availability or define a separately reviewed, auditable recovery mapping that preserves original evidence; never disable immutability guards or silently rewrite submitted/publication proof to make the drill pass.
6. Include negative fixtures: missing version, changed bytes/checksum, denied KMS key, wrong organization, revoked reviewer/assignee, held expired evidence and already disposed data. Missing/unverified bytes remain inaccessible and operationally visible; restore does not grant a synthetic clean scan or resurrect access to disposed/revoked evidence.
7. Reconcile durable queued/leased jobs against the restored state before restarting dispatch. A restore can resurrect an older pending event after an external effect already happened. Reconcile delivery/provider receipts and idempotency references through the communications design; do not replay all outbox rows indiscriminately. Recover from PostgreSQL state rather than assuming Redis is authoritative. Start one scheduler only after the reconciliation decision.
8. Record backup age, achievable recovery point, elapsed restore and validation time, missing/unresolved records, operator and cleanup result. Compare measured values with approved RPO/RTO, record deviations and keep real traffic disabled until the restore is accepted.

Do not conduct a restore drill against an existing development/shared acceptance database or production bucket. Guard the resolved target names/paths before any deletion; clean up only resources created and owned by the drill. Restoring a backup does not authorize real provider messages or public traffic.

## Monitoring and runtime acceptance

Existing request correlation and sanitized readiness logs are useful foundations. Add signals whose meaning matches actual behavior:

| Area | Minimum useful signals and synthetic failure evidence |
| --- | --- |
| API/web/edge | Request duration/error counts by bounded route class and status, readiness transitions, saturation and upload rejection counts; exercise timeout and dependency failure without leaking raw paths or credentials. |
| PostgreSQL | Connections/pool pressure, slow/bounded-query evidence, storage/backup age and restore verification age; prove connection loss and recovery. Load assumptions precede approved performance/error budgets. |
| Worker/Beat | Actual queue round trip, oldest due job/outbox age, active/expired leases, attempts/exhaustion, dispatch/retry/replay counts and scheduler liveness. Kill only owned test workers after claim and prove fenced recovery and terminal settlement. A healthy Redis ping is not worker/Beat health. |
| Files/scanner | Oldest quarantine/scan age, scanner availability/signature age, rejected/ambiguous checks, abandoned-upload/disposal backlog and unresolved versions; prove private-network failure, stale signatures, checksum mismatch, retained holds and recovery. |
| Communications/Meta | Pending age, safe failure categories, exhausted attempts, callback verification and ambiguous outcomes; exercise scripted/sandbox adapters only under their separately applicable authorization. Alert evidence never includes a destination, token, message body or provider payload. |
| Backup/operations | Last successful backup, verification/restore age, failed backup and nearing-capacity conditions. Alerts require a named responder, escalation path and runbook; local tests use a recording sink. |

Thresholds, availability objectives, load assumptions and alert contacts remain owner decisions supported by measurements. Avoid invented throughput, latency or uptime promises. Run applicable Linux process/time-limit/confinement checks and Windows/mobile checks on the platforms they claim to cover; protocol stubs do not replace live provider/runtime acceptance.

## Release checks and owner decisions

Before any real staging run, prepare the full configuration and a reviewable deployment/rollback procedure, then obtain the applicable hosting/provisioning/deployment authorization. The present authorization covers preparing those artifacts locally. It does not authorize creating paid resources, DNS/TLS changes, uploading source/images to external registries, contacting providers or sending alerts/messages.

| Owner or environment dependency | Evidence needed |
| --- | --- |
| Operations/client | Hosting/region/domain, approved recurring costs, isolation and secret/key custody, backup/RPO/RTO/retention, incident and alert owners. |
| Privacy/program/support/content owners | Real application/document/consent/retention/deletion rules; approved English/Tamil content, support policy, sender templates and business-publication consent. Local synthetic policy is not real collection approval. |
| Engineering/release | Exact intended revision passes backend/web/mobile/contracts/scans and accepted browser/runtime checks. Immutable image digest, container scan/SBOM and configuration/migration identity match that revision. Current dependency scans must remain unsuppressed. |
| Runtime/provider owners | Real isolated S3/IAM/KMS/version behavior, ClamD freshness/isolation, Redis/worker/one-Beat crash recovery, native devices and specifically approved provider sandbox results. Record unavailable gates accurately. |
| Security/accessibility/performance owners | Least-privilege and negative authorization evidence, capability-safe logging, keyboard/screen-reader and English/Tamil responsive review; measured representative load/query plans reconciled to approved budgets. |
| Client UAT/release approver | Critical public/applicant/reviewer/staff/student/mentor/alumni journeys accepted; admin provisioning/privilege review, training/guides, handover and stabilization owner assigned. |

The intended release procedure is: verify immutable artifacts and accepted restore → approved compatible migration → authorized rollout → health/runtime/critical journey smoke → monitor and obtain acceptance. Prefer rollback to the previous application artifact with compatible schema. Never perform a destructive schema downgrade against live data as a routine rollback; it requires its own reviewed recovery plan and authorization.

Produce a dated staging-operations report that lists each gate as passed, failed, deferred or unavailable, with source/artifact identities and links to sanitized evidence. Report local artifact completion separately from staging deployment, staging acceptance, client UAT and production release. No unchecked or unexecuted release gate becomes complete merely because later independent local implementation proceeds.
