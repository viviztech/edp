# Authorized business tools plan

Prepared: 2026-10-24. Status: plan only for step 6 of the [remaining development sequence](remaining-development-plan.md). The owner authorized local implementation of digital card, catalogue, quotation and mini CRM in that order. Complete and report preceding checkpoints before implementation. No external publication, real contact collection, messages, accounting claims or deployment is implied.

## Common owner boundary

Reuse `businesses.BusinessProfile` and its current `owned_enrollment` rules: active/completed participant and enrollment, owning global Person, organization and current `participant.self`. A UUID, staff role or membership alone never grants another entrepreneur's private tools. Keep the existing organization marketing CRM separate from the entrepreneur's customer records. Add migrations, relational scope/identity/version constraints, current server authorization, safe audits, English/Tamil web integration and meaningful acceptance for each slice.

Use expected versions for updates and immutable request UUIDs/digests where creation can be retried. On lost or conflicting saves, preserve input, fetch authoritative state and reconcile explicitly; never replay an unknown non-idempotent write. Bound list pagination, text, item counts and monetary values. Audits record identifiers/versions/field names rather than contact or quotation contents. Approved retention and collection/sharing copy remain external gates; synthetic fixtures do not supply real policy approval.

## Ordered vertical slices

| Slice | Initial useful behavior | Required acceptance |
| --- | --- | --- |
| Digital business card | Owner edits explicit public-facing business details in both languages, previews the card, and makes a separate versioned opt-in publish/revoke decision. Existing `public_opt_in` records interest only; it must not publish retrospectively. Public projection includes only deliberately selected business fields and a stable share reference; exclude account email, enrollment, financial/support/outcome data and internal identifiers. Printable/downloadable card is a useful first artifact. | Owner/peer/other organization/revoked access, idempotent creation, stale/lost save recovery, explicit publish/revoke, anonymous minimal projection and immediate revocation. Public cache behavior must not preserve revoked content. Local tests use synthetic records and loopback previews. |
| Product/service catalogue | Owner manages bounded named products/services with bilingual description, availability and optional explicit price/currency. Private preview precedes a separate catalogue sharing decision. Product history remains consistent when referenced by quotations. Initial plain-text products do not require a parallel upload system; any image support must first bind to the established typed private-file/policy/scan gateways. | Scope/version/duplicate request negatives, bounded paging, inactive items, explicit anonymous projection and revoke, price precision, preserved edits and English/Tamil layouts. No account/private profile data leaks through a catalogue. |
| Quotation | Owner prepares a bounded quotation for an explicitly entered customer, with immutable issued snapshots, dates, currency and line items. Referenced catalogue values are rechecked under ownership and snapshotted; manual lines are explicit. Server computes decimal line totals/subtotal/adjustments/final total under one documented rounding rule. Provide a reviewable printable/export artifact and audit download. | Decimal/rounding/overflow and row limits, malicious text escaping, stale catalogue values, cross-owner references, idempotent issue, immutable issued content, authorized download and lost-save/issue recovery. Label quotations without statutory tax/accounting/invoice claims. Do not add payments or send the artifact externally. |
| Entrepreneur mini CRM | Owner privately manages customer/lead contacts and versioned follow-up tasks with due time, status and safe history. Keep lifecycle transitions explicit. Contact information is not public and is never automatically sent to the organization marketing CRM or a provider. | Owner/peer/staff/organization negatives, bounded contact/task filters, expected versions, current UTC dates, duplicate/lost writes, completion/history and English/Tamil loading/error/empty/recovery states. Any reminders use an explicitly supported channel/topic and preference; a stored task is not proof of delivery. |

Resolve exact field names, API shapes and artifact formats against the then-current source before coding each slice. Routine implementation choices remain within this authorization. Add only dependencies that materially serve an accepted feature and retain unsuppressed dependency/secret scans.

## Checkpoints and release boundary

After each useful slice, run affected guarded PostgreSQL/API and SQL-negative tests, strict backend checks, migration round trip/drift, deterministic OpenAPI/TypeScript generation, web component/BFF checks and production build, then a real synthetic browser journey and English/Tamil responsive/keyboard review. Broaden tests where changed shared behavior warrants it. Seal selected source and record actual evidence before the local checkpoint.

The final report separates locally accepted behavior from exact-revision remote CI, native tools/device coverage, approved sharing/contact/retention policy, live hosting, client UAT and production release. Public-route implementation and synthetic loopback previews do not establish authorization to publish real entrepreneur details.
