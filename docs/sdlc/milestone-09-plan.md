## Helpdesk contract

Authenticated routes use `/api/v1/helpdesk/organizations/{org}`. An owner needs `participant.self`, an active/completed participant and active/completed enrollment in that organization. Staff permissions are `ticket.view`, `ticket.assign`, `ticket.update` and `ticket.admin`: Support Executive gets the first three, Program Manager/Director and Super Admin also get admin. View/update permits only tickets currently assigned to that user; admin permits the organization queue. Assignment requires assign permission and either admin or current assignee; an eligible staff user may claim an unassigned ticket. Assignees must be active users with ticket.view and ticket.update in the same organization. No arbitrary staff user directory is exposed: a bounded eligible `/assignees` list is staff-only.

Ticket categories are funding, registration, tax_compliance, marketing, technology, business_planning, banking, mentoring and general. Priorities are low/normal/high/urgent; owners choose low/normal/high on creation, staff may set urgent with an audit reason. There is no implied SLA. Each ticket has a UUID, human-readable unique number, organization, derived owner, category, subject, current status/priority/assignee and optimistic version. Creation accepts a client UUID request_id, unique per owner/organization, to make lost-response retries safe; reusing it with changed input conflicts.

Lifecycle: open -> assigned (by assignment) -> in_progress -> waiting_for_user -> in_progress or resolved; in_progress may resolve directly; resolved -> closed. Owners may close a resolved ticket and reopen resolved/closed tickets to open with a meaningful reason; only the same owner or organization admin may reopen, retaining all history and clearing assignment. No skips or generic status PATCH. Message/status/assignment/priority operations require the exact ticket version and update it transactionally. Shared replies are owner/current-assignee/admin only; internal notes are staff-only and never enter participant DTOs, counts, notifications or history reasons. Freeze UI during writes and preserve input on errors; ambiguous/stale writes require refresh without automatic replay.

Immutable relational messages, assignment evidence and status/priority history accompany ticket changes. Owner-facing history excludes staff assignment reasons, internal notes and staff-only priority reasons. Audits store identifiers, field names and versions, excluding ticket subjects, bodies and private reasons. Organization-aware foreign keys, version/status guards and append-only evidence are enforced by PostgreSQL.

Routes: GET/POST `/tickets`; GET `/tickets/{id}`; GET `/tickets/{id}/messages` and `/tickets/{id}/history` with bounded cursor pagination; POST `/tickets/{id}/messages`, `/assignment`, `/priority`, `/status`, `/reopen`; GET `/assignees`. GET `/tickets` defaults to the owner's tickets for participants and assigned queue for staff, with an explicit admin-only organization queue. Filters: status/category/priority and bounded limit/cursor. The eligible staff `queue=unassigned` claim queue returns only ticket IDs, number, category, priority, status, version and timestamps; subject, owner, discussion and history remain inaccessible before assignment. A shared owner reply while waiting_for_user automatically resumes in_progress. Participant DTOs never expose staff-only fields.

Attachments are optional UTF-8 plain-text `.txt` files only, up to 32 KiB each and three per message; JSON accepts filename/content rather than arbitrary URLs or storage keys. Store private immutable attachment bytes/text under the message's organization/ticket. GET `/tickets/{id}/attachments/{attachment_id}` reauthorizes the ticket and message visibility and serves a no-store, nosniff attachment download. Reject binary, HTML/script, NUL/control payloads and misleading extensions; no inline rendering. Broader PDF/image uploads, object-storage scanning and real document collection remain the existing separate private-file release work.

Durable in-app notices contain only recipient/ticket IDs and event/version (no subject/body/internal note). Notify owner on shared staff replies/status changes and assignee on assignment/shared owner replies; never on internal notes. Notice creation is transactional and deduplicated. Each notice read/list rechecks current owner/assignment/organization authorization. GET `/notices`, POST `/notices/{id}/read`, GET/POST `/preference` expose recipient-only bounded inbox, exact-version reads and per-user opt-out. This is in-app availability, not external provider delivery; no email/SMS/push is sent.
