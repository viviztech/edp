# Configurable file-policy administration

The first secure-file workspace manages rules only. It does not accept or deliver file bytes, certify legal approval, enable collection, or configure a storage provider. `FILES_ENABLED` remains false by default and publication does not change that setting. Required documents and approved retention/notices remain owner decisions. Synthetic fixtures explicitly supply their own test rules.

Each organization/purpose has numbered editions, with an optimistic `version` for commands. Supported purposes are application documents, CMS assets, assignment submissions, learning materials and helpdesk attachments. A draft requires explicit name, allowed MIME types, maximum file size/count, both notice languages, positive ordinary/rejected retention days and an explicit frozen-evidence disposal choice. There are no document, notice, format or retention defaults. Legal holds still block disposal independently of the frozen-evidence choice.

The supported rule envelope is PDF/JPEG/PNG/WebP/plain UTF-8 text metadata, 1–104,857,600 bytes per file, 1–100 files, 1–3,650 days for both retention fields, a name up to 160 characters and each notice up to 4,000 characters. These are validation bounds, not recommended or approved values. Later domain bindings must decide which of these formats can actually be collected and how the count applies. A policy alone does not authorize bytes.

`files.policy.view` permits bounded organization-scoped list/detail. Every mutation additionally requires `files.policy.manage`. The initial role seed grants both only to Super Admin and Program Director, through their existing organization assignments. A manage-only custom grant does not bypass view checks. The account/staff navigation includes the workspace only for view-capable grants.

The API is `/api/v1/files/organizations/{org}/policies`: GET list/detail, POST draft creation, PATCH a draft, and POST `/{id}/publish` or `/{id}/retire`. Creation uses a required `client_request_id` UUID and normalized payload fingerprint; exact replay returns the same record and changed reuse conflicts. The server assigns the purpose edition. A purpose can have only one draft and one published edition. Optional `copy_from` is confined to the same organization/purpose and a published or retired source. The copied rule values are explicitly supplied and reviewed, rather than implicitly published.

Draft changes and lifecycle commands require the exact `expected_version` and a bounded reason. Published/retired rules are immutable. Publication atomically retires the prior active edition for that purpose, while existing file evidence stays pinned to its original policy. Retirement preserves metadata; it is not evidence disposal. Core services and PostgreSQL guards own these transitions. The policy route/schema modules are thin boundaries over those authoritative services/DTOs.

The bilingual web workspace is `/{en|ta}/admin/file-policies?organization={org}`. It starts new drafts with blank rules and an unselected disposal choice. Publication and retirement need an explicit new reason. A copied edition remains a draft. Stale or uncertain existing-record writes pause commands until the operator loads the saved state, compares every rule and explicitly selects the current version. Entered rules remain available during that review. An uncertain creation freezes its exact input and UUID for a manual idempotent replay; there is no automatic write retry. A confirmed write followed by a list-refresh failure is reported as saved and recovered through reads.

The closed Next.js `/api/file-policies` proxy forwards only the administration routes. It rejects generic files, upload/download, activation and deletion routes, unrecognized/repeated queries, queries on detail/mutations, cross-origin writes, missing CSRF, non-JSON/malformed UTF-8 and streamed JSON larger than 64 KiB. Complete bilingual notices fit within that boundary. Upstream cookies/provider paths/secrets are not exposed; staff responses are private/no-store/noindex. The server-only BFF key and browser session are forwarded only to the configured API.

Tests cover no invented defaults, explicit disposal/retention, idempotent uncertain creation, expected-version reconciliation, published immutability/copy, saved-versus-refresh failures, narrow rights, scope, byte/query/CSRF boundaries, paging and Tamil controls. PostgreSQL/core/storage/scanner verification and later domain byte flows remain separate acceptance evidence. This workspace alone does not complete Process 3 or approve production collection.
