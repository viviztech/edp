# CMS verified media

Recorded: 2026-10-23. CMS media uses the shared private-file foundation. Collection stays disabled by default. Synthetic acceptance does not approve a production policy or demonstrate a live scanner/object-store deployment.

Historical `cms_assets` scan/visibility flags remain recorded metadata. They never authorize bytes: a record without a typed source is explicitly `unbacked`, has no public URL and cannot publish. No digest, scan or derivative is backfilled. The former boolean scanner callback always returns `410 asset_scanner_callback_retired`.

`cms_asset_files` immutably binds a source or public derivative to its asset, organization, owner and `cms_asset` purpose through the complete shared-file foreign key. Both roles use the asset ID as resource context and share the original owner/pinned policy, so policy counts include both stored files. Database guards reject cross-context attachment, binding replacement, differing derivative owner/policy/MIME and publication without exact clean frozen proof. Replacing media creates a new asset.

Metadata and source intents use distinct client request UUIDs. Matching retries return the same record; changed reuse conflicts. Source registration requires expected asset version, a published media policy, MIME, byte count and SHA-256. Image policies explicitly require at least two files. The CMS ceiling is 10 MiB; policy may be lower. New metadata intentions use the configured actor/organization rate limit. Browser-supplied owner IDs, generic file IDs, resource IDs, keys or URLs never grant access.

Writes returning private details require both `cms.asset.view` and the exact `cms.asset.create` or `cms.asset.publish` permission; publish authority also controls revocation. Listing/detail/private source delivery require view. Slow upload buffering and provider reads reauthenticate current session/user/grants afterwards. The request session disables automatic expiry, so explicit identity expiry is necessary. Synchronous database/provider work runs outside the event loop.

Under `/api/v1/cms/organizations/{org}/assets`, endpoints are collection metadata `POST/GET`, `GET /policy`, detail `GET /{asset}`, `POST /{asset}/source`, `PUT/GET /{asset}/source/content` and versioned `POST /{asset}/prepare`, `/publish`, `/revoke`. Only the exact typed source PUT bypasses the JSON cap. Authentication, browser origin/CSRF, exact MIME, quoted If-Match, no encoded body and actual byte counting still apply. Registered size and operational limits are checked before storage claims. DTOs omit keys and provider versions.

Public image preparation reads a verified clean source. Pillow accepts only JPEG/PNG/WebP, one frame and at most 16 million pixels before decoding. A fresh canvas is encoded without inherited EXIF, XMP, ICC, text or comment metadata and with bounded output. The resulting private immutable derivative goes through normal verified upload and scanner leases; the encoder cannot mark it clean. Creating a derivative requires its source policy to remain published. Retired policy returns `asset_policy_retired`; a fresh asset under the current policy is required. Already-created derivatives may complete their pipeline. See [Pillow security guidance](https://pillow.readthedocs.io/en/stable/handbook/security.html).

Publishing selects the clean PDF source or separately clean image derivative. Versioned commands freeze evidence and atomically pin file ID/storage version/hash/size with publication and audit. Later legal-hold changes may advance operational file version without changing immutable publication proof. Domain binding creation uses shared internal transaction helpers without a partial commit.

`GET /api/v1/public/organizations/{org}/assets/{asset}/content` resolves current publication and typed role, checks exact clean scan identity and retention/deletion, obtains a verified private snapshot before headers, then rechecks publication. Revocation blocks future delivery; expiry blocks delivery even when a legal hold preserves stored bytes. Previously delivered/in-flight bytes cannot be recalled. PDFs are attachments; only sanitized images may be inline. Responses use no-store, nosniff, sandbox and generated names. No provider URL, presigned capability or provider header reaches the browser. The public web gateway forwards no browser session/BFF key and accepts only the typed asset path. Public metadata excludes private file details.

The bilingual workspace shows notices, limits, quarantine/scanner-unavailable/rejection states and unbacked records. Registration retains the file/draft and UUIDs on failure. A lost upload response is reconciled through the typed detail before any pending/expired upload retry. Writes freeze controls; stale publication preserves the explicit reason. Preparation, publication and revocation require a reason.

The workspace obtains mutation tokens from `GET /api/session/csrf`; the CSRF cookie remains HttpOnly. A real-browser check exposed that reading this cookie through JavaScript prevented every media write. Component regressions now require endpoint-issued tokens for metadata and raw bytes with no readable cookie, and preserve the selected file/title without sending a command if token retrieval fails.

Confirmed upload success and explicit new-registration discard reset the native file chooser as well as its local state. Uncertain writes keep the exact original selection for recovery. A cleared chooser can select the same original file for a fresh record without an intervening different file.
