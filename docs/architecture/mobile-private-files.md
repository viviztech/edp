# Mobile private files

Design checkpoint: 2026-10-24 (Asia/Calcutta). Implementation authority is [Flutter M02](../sdlc/flutter-domain-plan.md), the generated OpenAPI contract and the current application/file services. This note specifies local implementation after the M01 checkpoint; it does not claim native execution, enable collection or authorize real documents. Android/iOS execution remains an explicit gate under [ADR 0004](adr/0004-native-verification-deferral.md).

## Decision and boundaries

Use a small Android/iOS document-picker bridge that makes a bounded private snapshot before returning success. Keep the shared Dart transport, snapshot interface and application document repository separate. Subsequent assignment/helpdesk repositories can reuse the byte layer while retaining their own endpoints, policies, revision checks and object authorization.

Do not add an upload queue, provider-URI database, filename-based recovery, browser BFF access, generic file-ownership API, export/share intent or external viewer. Only the identity repository handles bearer credentials. A private snapshot contains no refresh/access credentials and its metadata never establishes domain ownership.

The official `file_selector` Android implementation examined during design allocates the provider-reported file size into a byte array before returning, then copies the source. A bounded Dart stream around that result would be too late. Its [native implementation](https://raw.githubusercontent.com/flutter/packages/main/packages/file_selector/file_selector_android/android/src/main/java/dev/flutter/packages/file_selector_android/FileSelectorApiImpl.java) and [Dart conversion](https://raw.githubusercontent.com/flutter/packages/main/packages/file_selector/file_selector_android/lib/src/file_selector_android.dart) support this choice. `file_picker` offers a stream API, but adding it still requires version-specific native-copy review; old `withReadStream` examples do not describe the current API. See its [maintained documentation](https://pub.dev/packages/file_picker).

The bridge uses platform APIs already present in the app, avoiding a new picker or document-renderer dependency. Any Dart hashing package imported directly must be declared directly even if already present transitively. No dependency upgrade is implied by this note.

## Private snapshot contract

The Dart-facing interface exposes an immutable snapshot handle with an unpredictable ID, exact byte length, lower-case SHA-256 and one supported media type. `openRead()` yields bounded chunks from the completed private snapshot; it never reopens the original provider document. `dispose()` is idempotent and deletes only the app-created snapshot. Source names and URIs are not required by feature code.

Use one private store per application process and random in-memory scope IDs for session/feature ownership. Feature code cannot supply absolute paths, URI strings, directory names or deletion targets. The native registry maps opaque IDs to files under its own canonical root. Native channel methods reject unknown IDs, closed scopes, nonpositive/out-of-range offsets and chunks larger than 64 KiB. Read/write calls provide sequential backpressure; the bridge must not enqueue an entire document in channel messages.

The channel may provide `pickSnapshot(scope, allowedTypes, maxBytes)`, bounded `read(handle, offset, count)`, `release(handle)` and scope cancellation. Download sinks use equivalent begin/append/finish/abort operations restricted to this registry. Only a successful `finish` produces a readable immutable handle. The transport does not receive native paths. Keep these methods narrowly internal; they are not web/API routes.

Create each file exclusively under an app-owned random subdirectory, write to a `.part` file and rename only after successful verification. Use fixed buffers, count every byte and stop as soon as the effective ceiling would be exceeded. Reject zero-byte input. Reported provider length is an optional early rejection hint; neither it nor a filename determines allocation size or successful completion. Hash the exact bytes written, including the final chunk. A failed copy, mismatch, cancellation or close removes the partial target.

Private snapshot writes have one writer and become read-only after completion. Before upload, verify the stored size and digest again; detect mutation rather than registering one proof and sending another. The upload stream also counts its bytes and verifies EOF. A mismatch after sending starts is an uncertain command requiring domain readback. Never retry using a reopened provider stream.

## Platform selection and storage

Android uses `ACTION_OPEN_DOCUMENT`, `CATEGORY_OPENABLE`, a single selection and only read access. MIME filters cover the allowed server types. Do not request broad storage/media permissions, directory access, write permission or call `takePersistableUriPermission`. Open the selected URI through `ContentResolver` on an IO executor, copy through a fixed buffer into internal cache and promptly close the descriptor/stream. Reject unsupported/virtual data that cannot supply the required bytes. URI/path conversion and source deletion are absent. Android's [document access guide](https://developer.android.com/training/data-storage/shared/documents-files) and [official open-document sample](https://github.com/android/storage-samples/tree/main/ActionOpenDocument) describe the platform selection boundary.

iOS uses a single `UIDocumentPickerViewController` with the allowed UTTypes and opening mode. Coordinate access to the selected external document with `NSFileCoordinator`, acquire security-scoped read access when required and release it in all exit paths. Copy on a background queue with bounded `InputStream`/file IO, rather than `Data(contentsOf:)` or an unbounded automatic import. Save no security-scoped bookmark. This follows Apple's [document-picker access requirements](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller). The current project targets iOS 15, so supported modern picker/UTType APIs are available at compilation time; execution remains unverified.

Keep Android files in internal cache and retain the existing `allowBackup=false`. Put iOS files under the private temporary/cache root, mark them excluded from backup and apply complete file protection to directories and files. Locked-device access failures remain failures; background processing must not weaken protection. Do not use Downloads, photo albums, public app folders, external cache or a shared `FileProvider`.

On startup, initialize the store once before feature use and remove only abandoned files matching the app's exact private-root/child naming contract. Resolve the root and child, reject symlinks/path traversal and never recursively delete a caller-provided directory. Bound cleanup work and the number/total bytes of live snapshots. A process restart does not adopt an old file or reconstruct an upload intent from leftover bytes. Record cleanup failure without filenames and deny further collection when the private store cannot enforce its bounds.

Release selected bytes on completed upload, cancellation/replacement, route disposal, logout/revocation and failed snapshot creation. An uncertain registration/upload may retain its current in-memory snapshot for explicit recovery while the feature remains active. Backgrounding pauses polling and cancels active transfers; uncertainty survives until authoritative readback. No automatic background byte continuation is added.

## Type and size validation

Picker filters and provider MIME/extension are hints. Determine PDF/PNG/JPEG/WebP from their bounded byte prefixes; inspect all text through a strict incremental UTF-8 decoder and reject disallowed control characters. Mirror the server's supported set (`application/pdf`, `image/png`, `image/jpeg`, `image/webp`, `text/plain`), signatures and text rules in test fixtures. Extension does not override conflicting byte evidence. Do not silently transcode, compress or rename the selected content into another type. A supported signature is not a clean antivirus result or complete document parser validation.

Effective upload bytes are the minimum of the pinned policy's `max_file_bytes`/`max_upload_bytes`, the current form/list operational `max_upload_bytes` and a documented bounded client ceiling. Zero/missing/invalid limits disable selection. Requirement and policy counts both apply; the server remains authoritative across concurrent devices. Display pinned English/Tamil notices, instructions, types, byte/count limits and retention before enabling the picker. Disabled collection supplies no picker, remove, upload or download byte control.

## Authenticated stream transport

Add a narrow file operation beside `DomainApi`, backed by the same identity session/refresh implementation. Do not use `requestBytes`'s accumulated `Uint8List` path for large files. Upload accepts only an immutable snapshot and exact typed relative endpoint; download accepts only a typed endpoint and expected proof. Neither accepts an origin, arbitrary returned URL or caller-selected local path.

Raw PUT uses the snapshot's exact media type as `Content-Type`, a quoted positive **file** version in `If-Match`, a transport-derived `Content-Length`, and the authenticated bearer. It supplies a `Stream<List<int>>`, with no multipart, filename, `Content-Encoding` or gzip transformation. A narrow transport parameter supplies derived length; do not open the public custom-header allowlist to caller-controlled lengths or authorization.

Commands are sent at most once. Authentication may be refreshed before a new explicit action; a 401, timeout, cancellation, malformed success or lost response never replays PUT. Preserve `Retry-After` for the UI without sleeping/retrying in the transport. Bound request/response deadlines; the current server body deadline is at most 90 seconds and its operational byte limit still applies. Progress reports bytes sent, never clean scan or completed submission.

JSON command responses must decode as `ApplicationDocumentResult`; malformed successful responses are uncertain. Streamed error bodies are bounded and reduced to stable safe codes, not logged or displayed as raw provider/server messages. Distinguish not-sent validation/session failure, definite rejection, forbidden/not-found, version/idempotency conflict, limit/type rejection, transient dependency failure and uncertain command outcomes.

Download reauthorizes the typed GET every time. Reject redirects and foreign origins before accepting bytes. Validate returned base MIME against the expected proof (allow the normal UTF-8 charset on `text/plain`), parse a valid bounded `Content-Length` when present and verify the actual byte count/digest before exposing the completed private handle. A missing length does not remove the streaming ceiling or expected-proof check. Never use `Content-Disposition` as a local path. Abort and delete partial output on any discrepancy or session change.

Capture the identity generation and feature scope before each asynchronous step. Session invalidation cancels Dio and native IO, closes the scope and disposes its handles. A late picker/stream response is discarded and cleaned up even if cancellation raced with completion. Recheck generation after body consumption and before publishing a handle/result. Page disposal prevents late callbacks from restoring private UI state. Safe-read authentication recovery may restart a rejected GET before accepting a body; a started partial sink is always aborted first.

## Application command/recovery states

The repository alone constructs `/applications/organizations/{org}/applications/{application}/documents` and its typed detail/content children after UUID validation. POST registration preserves the exact `client_request_id`, body and snapshot. A lost POST is recovered only by explicit replay of that same intent; a different body needs a new UUID. Repeated registration is supported by the existing server contract, including acknowledged registration recovery after submission. Do not invent an idempotency header.

An acknowledged registration advances `application_version` without replacing scalar answers. Refresh the exact application and reconcile any concurrent scalar change; retain dirty local text. On uncertain PUT, GET the known document detail first. `quarantined`/`scanning` require bounded reads, not another upload. `uploading` does not reveal lease expiry in the current DTO, so the client cannot infer permission to resend. Only current `pending` plus identical registered size/hash/type permits an explicit continuation. Infected/rejected/deleted or changed proof requires an explicit server-permitted new binding/removal path.

List/detail freshness and `usable` determine readiness. A `clean` label alone is insufficient. Preserve replacement as a new immutable binding with `replaces_document_id`; removal includes expected application version. Render submitted evidence from `submitted_evidence.file_version/sha256/byte_size/frozen_at`, even when the operational file version later changes. A successful byte upload never freezes evidence or submits the application.

After process death, reload owned server bindings and discard transient intent/snapshot references. A user may explicitly reselect content for a known pending binding only after the new bounded copy matches its registered size/hash/type and the current detail still permits continuation. An unknown registration is not recovered by matching a filename.

## Private download receipt and preview

M02's initial download result is a localized **verified private-download receipt** showing media type, size, hash and evidence date/version where applicable, with an explicit close action that deletes its handle. PDF/image content is not opened automatically. No OS viewer, URL launcher, WebView, share sheet, account-bearing URI or public file URL is involved. This gives testable download/readback behavior without introducing an unreviewed document parser or leaking private bytes to another app.

If a later slice adds inline images, bound decoded dimensions/pixels before rendering, use a downsampled app-local image and release the image cache on close/logout. A later PDF preview needs an explicitly reviewed in-process renderer, disabled links/scripts/attachments, bounded page count and raster dimensions, and native parser/resource tests. Server signature/scan acceptance does not establish that a preview parser is safe. Neither extension is required to complete this first receipt-based slice.

## Required evidence

Deterministic Dart/native-adapter tests cover zero/unknown/lying lengths, all supported signatures, split UTF-8, over-limit/truncated/mutated bytes, derived headers, redirect rejection, generation/cancellation races, cleanup ownership and bounded backpressure. Controller tests cover exact intent replay, changed UUID conflict, read-before-resend, one PUT on lost-response recovery, unusable clean evidence, replacement/removal, frozen proof and preservation of scalar edits.

Guarded synthetic API tests cover actual owner/peer/other-organization/revoked access, policy/operational limits, clean/unsafe/unavailable scans, submission gating, immutable evidence and fresh download denial after revocation. A loopback fixture may use controlled private storage/scanning only inside its owned isolated environment; no general collection/provider setting is enabled.

Compile Android where tooling exists and retain iOS code for macOS compilation. Real Android/iOS tests must still establish provider URI handling, cloud/unknown-size input, cancellation during copying, process death, locked-device protection, cleanup/backup exclusion, lifecycle and private receipt behavior. Mocked streams, successful builds and loopback API tests are separate evidence, not device acceptance.

## Native implementation checkpoint

The Android [bridge](../../apps/mobile/android/app/src/main/kotlin/com/example/edp_mobile/PrivateFilesBridge.kt) and iOS [bridge](../../apps/mobile/ios/Runner/PrivateFilesBridge.swift) implement the same `edp/private_files` methods. Each permits at most eight scopes, eight snapshots/sinks and 40 MiB of registered content; one file is capped at 10 MiB and each channel chunk at 64 KiB. A single serial IO queue provides backpressure. New private files are created exclusively and renamed only after completion. Supported binary signatures and strict streaming UTF-8/control-character checks match the server's file validator.

Android uses internal cache, read-only `ACTION_OPEN_DOCUMENT` selection and cancellable descriptor reads. Detaching the Flutter engine cancels selected-source IO, closes pending picker results, unregisters the channel and queues deletion of that bridge's scopes. Paths must equal their canonical forms; a symlink alias to a sibling private entry is rejected before reading or deleting. Failed download completion deletes its partial sink.

iOS registers through the implicit Flutter engine's plugin registry and includes its source in the Runner build target. It uses the registrar's current view controller without retaining a picker presenter; this follows Flutter's [registrar contract](https://api.flutter.dev/ios-embedder/protocol_flutter_plugin_registrar-p.html). Selection uses opening mode, no bookmarks and no automatic import; `NSFileCoordinator` and temporary security-scoped access surround the bounded snapshot copy. Copy timeouts have a per-copy generation so a late deadline cannot cancel a subsequent selection. Private directories/files have complete file protection and backup exclusion; completed snapshots are read-only. Startup and scope cleanup reject symlinks and remove only validated, app-created children. The empty scope directory is removed with `rmdir`, without recursively deleting a supplied target.

Local verification on this Windows host checked the unchanged channel contract, iOS property-list parsing, Xcode source registration and whitespace integrity. No Android SDK/JDK/Kotlin compiler or Swift/Xcode compiler was available to compile these native additions. The Android/iOS compile and real-device gates therefore remain **deferred**. Source review does not establish cloud-provider cancellation, platform data protection, engine lifecycle, picker or backup behavior; those require the device matrix above.
